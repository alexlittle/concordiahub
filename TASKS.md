# Tasks: split ConcordiaHub into a core package and an examples repo

Goal: `pip install concordiahub` gives a small, lean library and dashboard. The
examples and their large data live in a separate repo (`concordiahub-examples`)
that people clone for a first run. The core repo's git history is squashed so it
no longer carries ~7 GB of data.

## The three components

| Component | What it is | Where it lives | How people get it |
|---|---|---|---|
| **Core framework** | `concordiahub/`: the library, the dashboard and the CLI | The existing repo (squashed), published on PyPI | `pip install concordiahub` |
| **Examples code** | The `ex01…ex07` scripts, `helpers.py`, prompt templates and `evaluation/` scripts | The new `concordiahub-examples` repo | `git clone`, then `uv sync` |
| **Examples data** | Precomputed models, LLM outputs, caches and the example datasets | Outside git: a Release, Zenodo or Hugging Face download | `fetch_data.py` in the examples repo downloads it |

How they connect on a first run:

1. The examples code depends on the core framework, installed from PyPI.
2. `fetch_data.py` downloads the examples data into a folder.
3. The dashboard (part of the core) reads that folder via `--data-dir`.

The core never depends on the examples code or the data. That is why a user who
only wants the library gets a small install. The data is not in git and not on
PyPI; it is just files hosted somewhere, which is why it needs its own phase.

Work through the phases in order. Phases 1-2 are non-destructive; the
destructive steps (history rewrite, force-push) are all in Phase 6 and must not
be started until everything before it is done and verified.

Current sizes, for reference: `.git` 6.7 GB, `data_store1` 745 MB (of which
`medsynth_xgboost` is 646 MB and `medsynth_baseline` 59 MB), `examples/data/`
94 MB, `examples/cache/` 36 MB.

## Phase 6: Squash the core repo history (destructive)

Only start once Phases 1-5 are done and the backup in 0.1 exists.

- [ ] **6.1** Make sure the working tree is clean and committed. Note existing
  branches (`git branch -a`) and tags (`git tag -l`); decide which to keep.
- [ ] **6.2** `git checkout --orphan fresh-start`
- [ ] **6.3** `git add -A` and check nothing large is staged:
  `git ls-files -z | xargs -0 du -ch | sort -h | tail -20`
- [ ] **6.4** `git commit -m "Initial commit of ConcordiaHub (history squashed)"`
- [ ] **6.5** `git branch -D master && git branch -m master`
- [ ] **6.6** Delete old branches and tags locally (for example `eval-round2`) so
  nothing still points at the old history.
- [ ] **6.7** `git push --force origin master`
- [ ] **6.8** Delete old branches and tags on the remote:
  `git push origin --delete <branch>` and `git push origin --delete <tag>`
- [ ] **6.9** Shrink the local repo:
  `git reflog expire --expire=now --all && git gc --prune=now --aggressive`,
  then check `du -sh .git`.
- [ ] **6.10** Re-create any tags and releases that are still needed, on the new
  history.
- [ ] **6.11** If the old objects must be purged from GitHub (not just hidden
  from new clones), contact GitHub Support. Old commit hashes and PR refs can
  remain reachable until they garbage-collect.

## Notes

- The two repos are coupled by the `concordiahub` version pin in the examples
  repo. After each core release, bump the pin and re-run one example.
- Anyone with an existing clone or fork of the core repo has to re-clone after
  Phase 6. Open PRs against `master` will break.
